# 约束满足与可达性（`constraint-satisfaction`）

> 领域：通用。工作结构：`candidate_tree`。

```yaml
id: constraint-satisfaction
name: 约束满足与可达性
workbench: candidate_tree
recognize:
  surface_cues: ["有没有办法", "一家家试都被拒"]
  structural_checks: ["约束能逐条列清楚", "候选能列举，并能逐条对照约束"]
  discriminating_test: "能不能把每个候选对照约束逐条打勾？不能（选项连续、目标是最优）→ 转优化与对偶"
```

**识别特征**：要找"能做到的办法"；有不可违反的条件；选项离散。

**方法步骤**：

1. 约束先行剪枝：违反已确认硬约束才淘汰
2. 按"每个候选要求什么前提"分组，不按名字或品牌分组
3. 同层失败两次 → 提冲突核，把共同原因变成子目标，上跳
4. 全部出局 → 重审搁置项 → 查类别是否漏 → 提可放松的约束

**合适表示**：候选树：按前提分组的类别 → 具体候选。

**在原问题里怎么验证**：在原问题里实际尝试（申请、下单、跑代码），或查条款原文。

**适用假设**：约束能列清楚；候选能列举。

**失效信号**：每试一个就冒出一条新约束 → 约束没收集完，回 ①；候选多到列不完 → 转搜索与筛选。

**常见陷阱**：按品牌逐个试，看不见共同卡点；用软偏好或未核实的说法淘汰。

**例子**：用 ITIN、零信用、无固定收信地址办信用卡。
